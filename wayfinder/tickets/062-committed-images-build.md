## Question

Build what [committed-images](wayfinder/tickets/056-committed-images.md) settled. Nothing here is a decision — that ticket made fourteen and this one spends them. It is separate from [bcc-cli](wayfinder/tickets/055-bcc-cli.md) because almost none of this is CLI work: it touches the sheet, the editor's Export menu, SPEC, four committed files and the README.

**The sheet, and the renderer.** `CanvasSheet.svelte:130` gains `xmlns="http://www.w3.org/2000/svg"` on its one `<svg>` — the whole of decision 1, covering the four lane glyphs and the footer legend keys at once, with a regression assertion in `render.test.ts` beside the XHTML-shape guards at `render.test.ts:191-197` (an attribute whose effect nobody can see is an attribute that gets refactored away). `sheetSvg` draws the sheet in `FRAME_CSS` like `sheetDocument` does, which is decision 3 and a real fix: today the SVG lays out at a 1440px content box where every other surface uses 1360, and `FRAME_CSS`'s own comment already claims otherwise. Both changes rebuild `src/lib/render/dist/render.js`, which cascades into `cli/`'s inlined bundle — hence the ordering behind [bcc-cli](wayfinder/tickets/055-bcc-cli.md) rather than ahead of it.

**The editor's fifth export.** `svg` joins `ExportKind` (`src/lib/model/filename.ts:10`) and the Export menu gains **"SVG image"** fourth, between PNG and Markdown. It measures the way `png.ts:45` already does — `getBoundingClientRect` on the offscreen mount — and hands the height to `sheetSvg`. One-way: Import… is untouched. `writing-copy` for the menu entry and for the CLI's no-Chrome refusal if that lands here rather than in [bcc-cli](wayfinder/tickets/055-bcc-cli.md).

**The four files, and the README.** `examples/*.bcc.svg` beside their JSON, all four committed, with `*.bcc.svg -diff` in `.gitattributes`. The README grows **one** image — Order Fulfillment, above the existing list — wrapped in a link to its `.bcc.json`, which is decision 11's whole recourse for a reader who suspects the sheet is stale. Each file carries the CC BY comment `.bcc.html` already carries.

Two things left in the way by [remark-plugin](wayfinder/tickets/057-remark-plugin.md): `.scratch/stray-renders/` holds eight renders that were sitting untracked in `examples/` from [bcc-cli](wayfinder/tickets/055-bcc-cli.md)'s verification — delete them, this ticket authors the real four — and committing images makes `bcc.test.ts:152`'s `check` assertion read *"4 canvases check out."* plus an image line, which is this ticket's to update.

**The guard.** The repo's suite fails when a committed image is stale, by re-rendering at the height parsed out of the file under test and diffing the bytes — `server.test.ts:74-82`'s shape, and the same comparison [bcc-cli](wayfinder/tickets/055-bcc-cli.md)'s `check` leg calls, not a second implementation of it.

**SPEC.** §9.3 "SVG artifact" is written here and is the only place these constraints are stated: the fixed width and frame, the embedded fonts, the `xmlns` requirement, one-way membership, and 049's raw-URL caveat — opened directly the SVG is a top-level document under `default-src 'none'` and the embedded fonts genuinely are blocked, so a future reader files a bug against them unless this is written down. §3.4's family line and §10's menu entry gain their strings. `CONTEXT.md` wants an entry for **Render** if [bcc-cli](wayfinder/tickets/055-bcc-cli.md) has not already added one.

Done when the four images are committed and rendering on github.com, the README carries one, the suite fails on a stale image, `svelte-check` and both suites are green, and SPEC §9.3 exists.

## Resolution

**Built, and the editor's fifth export lands on the same bytes the CLI committed** — `order-fulfillment.bcc.svg` downloaded from the running editor through Export → SVG image is byte-identical to the committed file `bcc render --svg` wrote, 206,623 bytes both ways, the browser in the editor and the browser the CLI drove agreeing on a height of 1292 to the pixel. That is [headless-renderer](wayfinder/tickets/054-headless-renderer.md)'s `.bcc.html` demonstration repeated on a second container, and it is what the ticket's "it measures the way `png.ts:45` already does" turns out to be worth: two independent measurements of the same page frame are the same measurement.

The four images render, the glyphs with them. [github-svg-probe](wayfinder/tickets/049-github-svg-probe.md)'s misdiagnosed first constraint cost exactly the one attribute [committed-images](wayfinder/tickets/056-committed-images.md) predicted — `CanvasSheet.svelte`'s `kindIcon` snippet now declares `xmlns`, which covers the four lane glyphs and the four footer legend keys at once — and `render.test.ts` asserts it over *every* `<svg>` the sheet emits rather than over a count, since the failure it guards is an attribute nobody can see the effect of on screen.

**The frame fix was bigger than one line, and the second half of it is the ground.** Decision 3 said `sheetSvg` should draw in `FRAME_CSS` like `sheetDocument` does, and drawing in it alone would have been a regression: `main` carries a 40px padding, the renderer's wrapper paints the paper ground *inside* that padding, and the committed image would have been a cream sheet in a white frame — visible in a README, worse in dark mode. So the root `<div>` takes the scoping class the way the artifact's `<body>` does, and the ground is neutralised on the inner of the two wrappers with the rule [headless-renderer](wayfinder/tickets/054-headless-renderer.md) wrote for the same reason: a second painting restarts the 32px drafting grid at the wrapper's origin. With the frame in place the two containers finally agree on 1360, and [bcc-cli](wayfinder/tickets/055-bcc-cli.md)'s handed-on constraint — `measure.ts` measuring a frame `sheetSvg` did not draw in, ~177px of slack per image — is retired rather than worked around.

**The staleness guard is `bcc check`, run by the suite, and it was proved rather than asserted.** `cli/src/bcc.test.ts`'s existing `check --root examples` leg gained the image line, so the suite's guard *is* the comparison anyone else's `bcc check` runs, with no second implementation to drift. Breaking one committed image failed it as intended, naming the file and the command that fixes it. One guard the ticket did not ask for sits beside it in `examples.test.ts`: every roster entry must have a `.bcc.svg` on disk. It answers a different question — a fifth example arriving with no image would draw as a broken picture in whatever pointed at it, and a check that only ever compares files that *exist* can never notice.

Six other calls, of which three matter. The CC BY comment is now **one string in the renderer** (`CREDIT_COMMENT`) rather than a second copy in the SVG container, with `artifactDocument` rewired to it and its bytes unchanged — a licence sentence duplicated across two file containers is how one of them ends up without it. **`.gitattributes` did not exist**; it does now, and says why `*.bcc.svg -diff` rather than only that it is set. And SPEC took three amendments beyond §9.3 and the two named: §8's AA claim exempts *the two images* rather than PNG alone, §9's "the two artifacts are pixel-identical" became "the artifacts", and `CONTEXT.md`'s **Artifact** and **Unexported changes** entries were rewritten — the ticket named only **Render**, which [bcc-cli](wayfinder/tickets/055-bcc-cli.md) had already written and which already named the SVG container. Three smaller ones: the editor's SVG export is a dynamic import like the HTML one (an editor session that never exports an image has no use for ~200 KB of embedded faces); `markdown-export.test.ts`'s "fourth entry" test is now the fifth-and-last entry test, and the menu's one-way comment moved above PNG where it now governs three entries; and the README grew a sentence under the list beside the image, because a reader who sees a picture in a README has no way to know a check keeps it honest.
