# Wayfinder map: an MCP server for BC Canvas

## Destination

A local **stdio** MCP server living in this repo at `mcp/`, launched with `--root` and reusing `src/lib/model/*` unchanged, that lets an agent draft a Bounded Context Canvas from a codebase and read committed ones as context. Four tools — `bcc_list_canvases`, `bcc_read_canvas`, `bcc_write_canvas`, `bcc_explain` — canvases as templated `bcc://canvas/{path}` resources, and one `review-canvas` prompt. The curated vocabularies and the SPEC §10 section questions ride in the tool schemas and in `bcc_explain`, so the ddd-crew method travels with the tools rather than being reconstructed by whatever model is driving. The map is done when the **round-trip property** holds — bytes the server writes open unchanged in the app, bytes the app exports read unchanged in the server — and all four tools plus the prompt are exercised once in Claude Code and once in Claude Desktop. A second gate closes the workshop phase: the facilitation layer ships as a plugin — the server plus the `canvas-workshop` and `draft-canvas-from-code` skills and the `canvas-reviewer` agent — installed the way a user would install it, and driven through one real facilitated session in both hosts, with row fidelity checked on disk.

## Notes

- **This map carries execution** (like the hosting and examples maps): task tickets build and verify once the decision ticket clears.
- **Settled context (from grilling, 2026-08-09 — see [mcp-server-shape](wayfinder/tickets/025-mcp-server-shape.md) for the full resolution):** local-first, for Mitchell alone; publishing is a later decision made on evidence, so `package.json` stays `private`. Canvases are treated as committed repo files — that is the *workflow*, not something the server enforces; it takes a `--root` (defaulting to CWD) and works the same whether that root is a checkout or a plain folder. Both Claude Code and Claude Desktop are targets, which is what justifies a server over a skill-plus-CLI: reach into hosts with no filesystem. Day one is authoring-from-code and reading-as-context; the facilitated workshop is deferred. Whole-document write only — `bcc_edit_canvas` and its natural-key addressing wait for the workshop, which was its only real customer. Git is the conflict guard and the undo; the server does no mtime or revision checking. Off-vocabulary values are **accepted with a note**, matching SPEC §4's escape hatch exactly — a server stricter than its own editor is the Contexture trap [ticket 001](wayfinder/tickets/001-contexture-schema-lessons.md) recorded.
- **Protocol target:** revision **2026-07-28** (final, published 2026-07-28), TypeScript SDK v2 (`@modelcontextprotocol/server` 2.0.0, published 2026-07-27). Note the trap: v2 does **not** speak 2026-07-28 by default — `server.connect(new StdioServerTransport())` stays on the 2025-era protocol. Serving the current revision over stdio requires `serveStdio(() => buildServer())`, with legacy clients accepted (not `legacy: 'reject'`), because ecosystem migration is early: last-week npm downloads run ~52M for the v1 SDK against ~2M for v2. [mcp-package-scaffold](wayfinder/tickets/027-mcp-package-scaffold.md) found the mechanism: the modern era is claimed per-request in `_meta`, not negotiated by `initialize`, which is why a hand-wired transport cannot reach it — and why `LATEST_PROTOCOL_VERSION` in the SDK reads `2025-11-25`.
- **Research:** [`docs/research/mcp-server.md`](docs/research/mcp-server.md) — the primary-source pass on the 2026-07-28 spec, the SDK surface, prior art, and the token measurement that decided tool grain. Read it before any implementation ticket; note that its §5.2, §7.2 and §7.3 are superseded by [mcp-server-shape](wayfinder/tickets/025-mcp-server-shape.md) where they differ.
- **The seam (from [workshop-shape](wayfinder/tickets/031-workshop-shape.md)):** the server owns content and validation — SPEC §10 verbatim, vocabularies, parser, canonical bytes, digest; plugin components (skills, the agent) own only procedure and never restate what `bcc_explain` returns. No tool declares an `outputSchema`; every result speaks in prose. Both are standing rules for anything added later.
- **Skills:** `/grilling` for decision tickets (maintain `CONTEXT.md` as terms sharpen); `writing-copy` for every model-facing and user-facing string — tool descriptions, `bcc_explain` prose and the `review-canvas` body are copy, and the model is a reader; `/tdd` where the byte-identity properties are the point.
- **Tracker (local markdown):** tickets live in `wayfinder/tickets/*.md`. Frontmatter: `status: open|closed`, `assignee` (non-empty = claimed), `blocked-by: [ticket names]`. Frontier = open, unassigned, all blockers closed. Resolutions are appended to the ticket under `## Resolution`, then `status: closed`. Commit tracker changes to `main`.

## Decisions so far

- [Grilling: what shape is the MCP server?](wayfinder/tickets/025-mcp-server-shape.md) — local stdio server in `mcp/`, `--root` defaulting to CWD, both hosts; four tools day one (whole-document write, no edit tool), `bcc://canvas/{path}` resources both-doors, `review-canvas` shipping with them; vocabularies as full one-liners in the write schema generated from `vocab.ts`, no example resources, digest in words not glyphs; `parse.ts` gains a path-carrying refusal with app copy unchanged; git is the conflict guard; `mcp/README.md` owns the docs and SPEC takes only the parse amendment.
- [Task: give parse.ts a path-carrying refusal, without changing what the app says](wayfinder/tickets/026-parse-refusal-detail.md) — `ParseResult`'s `not-canvas` branch carries an optional `detail` reading `<path>: expected …, got …`, paths written the way a developer would type them (`inboundCommunication[1].messages[0].type`); "got" is the type in words except where the value is the problem (the message-type enum, `version`); `null` on an optional field teaches the omission rule; non-shape refusals quote the JSON engine message, and `parseCanvasImport` names both doors when a text is not JSON at all; SPEC §3.3 gains one bullet; the app's two §10 sentences are pinned by a new `chrome/import-refusal.test.ts` that also proves no fragment of the detail leaks into the dialog.
- [Task: scaffold the mcp/ package — build, transport, root and containment](wayfinder/tickets/027-mcp-package-scaffold.md) — `mcp/` is a private package with its own `node_modules`, bundled by esbuild to `dist/server.js` through a `$lib/* → ../src/lib/*` tsconfig mapping (no `baseUrl` — TypeScript 6 errors on it); `serveStdio` with no `legacy` option puts 2026-07-28 on the wire and still serves 2025-era clients, both pinned by driving the built server as a subprocess over raw JSON lines; containment resolves symlinks before comparing, covering the not-yet-existing path behind a symlinked directory; `console` is rebound to stderr at import time so a stray log cannot corrupt the stream; `serializeCanvasFile` lands in the model layer by widening `toCanvasFile` rather than duplicating the key order.
- [Task: the four tools, the canvas resource, and the tests that pin them](wayfinder/tickets/028-mcp-tools-and-resource.md) — the four tools ship in fixed `tools/list` order with the vocabularies generated into the write schema and `z.enum` only on `message.type`; the digest is markdown mirroring the artifact's headings, types in words, empty sections named once at the end, and measures 1.6 KB against 3.3 KB of JSON; `bcc://canvas/{+path}` carries the digest and the exact bytes under one URI; a real client over an in-memory transport drives all of it, and every committed example survives read-then-write byte for byte. Two findings: ticket 026's detail teaches on the *read* path, since the input schema is stricter than the parser on the write path; and `tools/list` costs 12.7 KB, not the 1.5 KB decision 13 sized — the vocabularies were only ever part of it.

- [Task: the review-canvas prompt and the server's README](wayfinder/tickets/029-review-prompt-and-readme.md) — `review-canvas` takes a required `completable()` `path`, embeds the digest as an embedded resource under the canvas's own `bcc://` URI, and closes with a prohibition on answering the questions or drafting the missing rows; a bad path throws `ProtocolError(INVALID_PARAMS, …)` so the accepted cost really is `-32602`, and the sentence it carries moves into a shared `readProblem` that `resource.ts` now uses too. `mcp/README.md` covers both hosts split by why each needs `--root` or not, the four tools and the prompt, the discovery skip list, the extension rule, the last-write-wins tab warning with its remedy, and the protocol line; the root README gains a pointer.
- [Task: the destination gate — round-trip holds, both hosts drive it](wayfinder/tickets/030-mcp-hosts-checkpoint.md) — the round trip closes byte for byte in both directions, `.bcc.html` included; Claude Code drives all four tools and `review-canvas`, Claude Desktop drives the tools while Cowork surfaces no MCP prompts at all — a host's choice, with `prompts/list`, `get`, completion and `-32602` green over real stdio. Four defects found by driving it and fixed here: refusals running two sentences together, an overstated digest saving, one unreadable directory aborting the whole listing, and containment inverted for a root of `/` (which is now refused at launch). Four findings carried to the workshop — `outputSchema` throwing the prose away in both hosts, discovery's five-name ignore rule, `--root` fixed at config time, and the prompt's problem being discovery rather than quality.
- [Grilling: what does the facilitated workshop need, now that day one has been driven?](wayfinder/tickets/031-workshop-shape.md) — the facilitation layer ships as a plugin: `canvas-workshop` and `draft-canvas-from-code` as skills (findable from `/` in every surface, which dissolves finding 7), `canvas-reviewer` as a thin agent, `review-canvas` kept as the sole prompt — the one entry point that runs with no tools and reaches non-Claude hosts. The seam: server owns content, plugin owns procedure. `outputSchema` dropped everywhere; discovery skips dot-directories; `--root` accepted as config-time; the built bundle committed and installed via a marketplace manifest in this repo; `bcc_write_section` not built, its trigger (a row lost or altered on disk) and shape (section-scoped, never an operation union) both named in advance; elicitation a dead fork.

## Out of scope

- **Artifact production — no PNG, no HTML.** SPEC §9 makes the shared read-only `CanvasSheet` component the canonical visual truth; the HTML artifact fetches the compiled stylesheet same-origin at export time and the PNG is a SnapDOM `foreignObject` rasterization. Both need a browser running the app. Reproducing them in Node means shipping headless Chromium or forking the renderer, and the second breaks SPEC §8.4's "editor and artifact cannot diverge". An agent that needs a shareable artifact hands the human a `.bcc.json` path.
- **The MCP Apps `ui://` preview.** It is the only honest way to *show* the quiet sheet without an export, and a first-party Svelte starter exists — but it would stand a second renderer path beside the canonical one, for partial client support. Revisit only if the workshop ticket produces evidence that people want to see the sheet rather than read the digest.
- **Undo/redo over MCP.** Undo is a session-scoped stack inside the editor (SPEC §6.1), cleared on import and never persisted; the server has no session and no such stack. The agent's undo is git. A `bcc_undo` would invent a second, weaker history nothing else respects.
- **Concurrency, locking, presence, mtime guards.** The app already chose last-write-wins plus a notice for multi-tab; a server that added locking would be stricter than the product it serves.
- **A canvas library, an index, or a cross-canvas context map.** `bcc_list_canvases` globbing a configured root is the ceiling. Relationships between canvases are a different product.
- **Remote/HTTP transport, hosting, auth, publishing to npm.** Reintroduces exactly what the main map fenced off, and drags OAuth 2.1 and RFC 9728 in as MUSTs. Local-first stands until real use argues otherwise; publishing reopens as its own map.
- **Foreign-format import** (Contexture, Miro, Excalidraw) — SPEC §1 out of scope, and the temptation is far stronger with an LLM in the loop that "could probably map it".
- **Writing `.bcc.html`.** The server *reads* one through `extractEmbeddedCanvas()`; writing one means rendering.
